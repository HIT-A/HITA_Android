# 课表版本、差异查看与教务变更通知设计

日期：2026-11-16
分支：`feat/ios-parity-migration`
代码基线：`645fc6fc`
状态：用户已确认并进入实现；实现与验证见文末记录。

## 当前约定：仅管理教务版本（2026-11-16 修订）

本节取代下文早期方案中“全部课程参与版本”的范围约定。

- 仅 `CLASS + EAS_IMPORT` 教务课次及其课程资料、开学日期和作息参与版本，保留最近五版（含当前）。手动课程、个人日程、考试、ICS 和分享导入内容不参与。
- 教务名称、时间、地点、教师、课程代码及学分等资料由教务维护，用户界面和写入层均拒绝直接修改。需要自行调整时，可复制成独立的个人日程。
- 颜色、个人隐藏状态、课表重命名与组合归属不参与版本；恢复历史教务版本时保留这些偏好。教务课可隐藏，并在课表详情中重新显示。隐藏偏好独立存放在数据库 v21 的 `teaching_visibility` 表，可靠识别的调课会继承偏好。
- 老数据中手动课次与教务课程共用资料记录时，先拆成独立个人资料，避免教务恢复连带改动个人内容。源端课程消失后保留其内部配色资料，课程列表不展示无课次的资料。
- 旧格式版本按教务内容读取并合并连续重复项。源端基线仍负责检测上游变化，不作为另一套用户历史；停止新增旧文件快照，仅在确有存量备份时显示兼容入口。
- 比较按课次标出调课、减少、增加；只有课程资料或作息变化时单独提示，恢复仍生成新的教务版本。

## 1. 目标与建议

建议采用类似 Git 提交历史的交互：用户看到的是一份份完整、不可变的「课表版本」，可以比较任一保留版本与当前课表，并通过恢复历史版本找回误删课程。

教务更新则以课次为单位归纳为三类：调课、课程减少、课程增加。简化的是展示，不取消现有的数据异常保护和采纳确认。

不引入真正的 Git 仓库、分支或远端同步；沿用本地数据库与现有课表数据源。

## 2. 现有实现与需要调整的地方

| 现有能力 | 实际边界 | 本方案处理 |
|---|---|---|
| 顶栏历史图标、删除历史页面 | 按单条删除记录恢复，不是完整版本 | 保留图标位置，替换成「课表版本」 |
| `EventEditHistoryStore` | 只接入部分写入，不能重建完整历史 | 暂留底层记录及旧数据，不把删除记录伪装成完整版本 |
| `TimetableSnapshotStore` | 账号＋学期隔离的教务课快照；不包含完整本地课程，空课表也不会捕获 | 保留旧数据的兼容读取；新版本使用统一课程快照模型 |
| `SnapshotRetention` | 默认 12、可配置，最高 40 | 新课表版本固定最近 5 条；旧数据不能直接全局裁剪 |
| `TimetableRefreshMergePolicy` / `CourseChangeConfirm` | 已有课次、周次、教师、地点差异，但展示较碎 | 复用可用的规范化逻辑，补充跨时段课次配对和三类摘要 |
| `TimetableChangeStore` | 待采纳、缺失观察、异常整批挂起、忽略记忆 | 保留状态机与保护规则，替换用户可见摘要 |
| `TimetableChangeRecovery` | 已有 Room 事务与文件发布 outbox | 延续提交后才发布摘要、失败可恢复的原则 |

当前缺失课程有「至少 3 次观察且跨越 48 小时」的升级保护。本设计默认保留，不因有版本回退能力就自动删除缺失课。

## 3. 版本对象与边界

### 3.1 版本属于哪一份课表

版本按「数据所有者＋具体课表」隔离，不按整个 App、显示组合或课程名共用。

- 教务课表绑定账号、校区、学期及本地课表身份。
- 本地手动／ICS／口令导入课表绑定其本地身份，不依赖教务登录。
- 组合课表只是显示关系；点击顶栏版本图标后先选择成员课表，避免把多份历史混为一份。
- 好友课表、培养方案预览等只读投影不作为可写版本目标。
- 删除整个课表的回收站不在本轮范围；版本不能复活已删除的课表对象。

### 3.2 版本包含什么

首期建议版本化课程部分：各来源的 `CLASS` 课次、课程归属及必要属性、隐藏状态，以及解释课程时间所需的开学日期和作息结构。

教务课、手动课、已导入的 ICS／口令课程均包含。独立考试和普通日程暂不参与课程恢复，页面明确注明「仅恢复课程，考试和普通日程不变」。这沿用当前教务版本恢复不影响考试、活动的边界，避免把课表回退扩大为所有日程回退。

不回退本地课表名称、组合归属、颜色、壁纸、主题、显示范围和提醒偏好。普通界面设置不产生课程版本。

隐藏课仍需进入快照的逻辑状态：隐藏／取消隐藏必须可比较和恢复；不能只查询 `hidden = 0` 后就丢掉必要状态。

### 3.3 最近五条的确切含义

建议严格保留最近 **5 个已提交版本，包含当前版本**：当前版＋最多 4 个历史版。界面直接写「保留最近 5 个版本」。

- 未采纳的教务变更是候选数据，不占用这 5 条。
- 教务比对基线、缺失观察记录不受此上限影响，不能被历史裁剪删掉。
- 使用单调提交序号排序，不能仅依靠手机时间判断新旧。
- 只在成功生成新版本后裁剪；失败操作不得挤掉旧版。
- 空课表是合法版本。删除最后一节课也必须保留可恢复的前一版。

若实际希望「当前课表之外再保留 5 条历史」，只需把此处调整为 6 个快照；本草案默认按总共 5 条设计。

### 3.4 时间语义

每个版本显示「最后修改：11 月 16 日 10:25」，对应这一版内容成功写入本机的时间，创建后不再变化。

- 刷新检查时间不是最后修改时间。
- 重复导入相同内容、打开页面、查看 diff，不更新时间，也不新增版本。
- 教务通常不提供可信的服务端修改时间，因此不能将本机检测时间标成「教务最后修改」。
- 旧快照若只能确定采集时间，显示「记录时间」，不补造最后修改时间。

## 4. 如何生成版本

### 4.1 以一次成功业务操作为提交单位

| 操作 | 是否生成新版本 |
|---|---|
| 首次启用／首次建立课程课表 | 建立当前基线版本 |
| 添加、编辑、删除单个课程课次 | 内容实际改变才生成 |
| 整门课、同一时段、多选批量修改 | 整次操作生成 1 版，不按课次刷屏 |
| 隐藏／恢复课程 | 生成 1 版 |
| 采纳一批教务变更 | 整批成功后生成 1 版 |
| 恢复某个历史版本 | 生成新的「恢复版本」提交 |
| 无变化刷新、失败、取消、忽略候选更新 | 不生成课程版本 |
| 换肤、改名、改颜色、组合管理 | 不生成课程版本 |

版本保存完整课程快照；diff 在比较时计算。只保留 5 版，优先选择易校验、易恢复的完整快照，不做脆弱的增量回放链。

### 4.2 恢复不是移动历史指针

例如 A → B → C，用户恢复 A，结果是 A → B → C → D，D 的课程内容与 A 相同，来源注明「恢复历史版本」。C 仍然可以比较和恢复，直到正常超出保留上限。

- 恢复前先展示与当前的差异及影响范围，再二次确认。
- 恢复前复核当前版本序号；若用户查看 diff 后课表又发生变化，重新计算，禁止按过期预览覆盖。
- 恢复成功后统一刷新网格、时间线、小组件和相关提醒。
- 恢复与版本追加必须同事务成功；成功后再裁剪旧版。
- 恢复不会改写教务源比对基线，也不自动清空尚未处理的上游候选；相关候选按新本地状态重新校验。

## 5. 界面方案

### 5.1 入口与版本列表

沿用时间表顶栏现有历史图标，辅助说明改为「课表版本」。不再显示删除历史列表。

点击后打开版本面板：

```text
课表版本                         保留最近 5 个

● 当前版本
  最后修改：11月16日 10:25
  手动编辑 · 调整 1 节课

○ 历史版本
  最后修改：11月16日 09:40
  教务更新 · 调课 1 节，增加 2 节
  [与当前比较]

○ 历史版本
  最后修改：11月15日 21:10
  删除课程 · 减少 1 节
  [与当前比较]
```

操作说明使用「手动修改／教务更新／恢复版本／初始版本」，用户不需要看到 commit、哈希或内部状态名。当前版本不显示无意义的「与自己比较」。

### 5.2 diff 的方向固定

页面明确显示：**所选历史版本 → 当前课表**。

- 「＋当前多出」：当前有、历史没有。
- 「－当前少了」：历史有、当前没有。
- 「调课」：能可靠配对的同一课次，显示旧时间 → 新时间。
- 地点、教师、名称等变化放在对应条目内作为属性差异，不冒充时间调课。
- 统计以「课次」计数，不把同一门课一学期 16 次上课算成 1 次。
- 调课配对后只计 1 次调课，不再重复计入新增、减少。

默认显示可读列表，并提供「周视图」切换：新增课次使用「＋」和边框，减少课次在原位置使用虚线／「－」标记，调课同时标出原位置和新位置，并关联同一编号。颜色不能是唯一标识；深浅主题下均使用现有令牌。

跨周调课支持切换相关周；同一周内的多条相同规则可以折叠成「第 3–8 周 周一第 1–2 节 → 周三第 3–4 节」，展开仍可核对每个实际课次。

「恢复此版本」位于 diff 页，确认文案直接写结果，例如「恢复后将增加 2 节、减少 1 节、调整 1 节；仅恢复课程」。这里的统计使用“当前 → 所选历史”的反向结果，不能复用页面正向计数。

## 6. 三类变更的判定

### 6.1 先规范化，再匹配

不能依赖导入时随机生成的 UUID，也不能仅凭课程同名判为同一门课。

1. 限定同一所有者、学期、课表及数据来源。
2. 优先使用稳定的源课程／教学班／课次标识。
3. 标识不足时，使用校区可提供的课程代码、教学班等组合身份；仅同名不够。
4. 先抵消时间与课程身份相同的未变课次，保留重复课次的数量，不做集合去重。
5. 对剩余课次尝试一对一配对；有稳定课次 ID，或课程身份和原教学单元等证据能唯一对应时，才合并成调课。
6. 多对多、不同教学班、仅“少 1 多 1”但无法确定对应关系时，分别展示减少、增加，不按最近时间强行配对。

不同校区缺少的标识要明确记录；不能为凑齐「调课」展示而虚构关联。

### 6.2 分类及文案

| 类型 | 判定 | 单条展示 |
|---|---|---|
| 调课 | 已可靠匹配的同一课次，日期／起止时间有变化 | `高等数学：11月17日 周二 1–2节 → 11月19日 周四 3–4节` |
| 课程减少 | 旧课次没有新对应项，也没有可靠配对的补课项 | `大学物理：11月18日 周三 3–4节减少，本次未发现对应补课` |
| 课程增加 | 新课次没有旧对应项，也未被配对成调课 | `离散数学：新增 11月20日 周五 5–6节` |

这里「没有补回来」只能表示当前有效数据中未发现对应补课，不能承诺以后不会补。后续若发现可信对应补课，应更新未处理的同一事件，而不是继续保留过时的“减少”结论。

仅地点／教师变化时生成版本并在 diff 详情展示；首期建议不发三类课程数量／时间变更提醒，也不算作调课。若需要地点变化强提醒，可以另行增加偏好，不混入这三类的定义。

## 7. 上游变更检测与通知

### 7.1 两种 diff 使用不同基线

- 版本查看：`历史版本 H → 当前本地课表 L`。
- 上游检测：`上次可信源快照 S → 本次完整源快照 N`。
- 是否采纳：结合本地修改与最近已采纳的源基线进行三方校验，不把本地改动当作教务变动。

例：用户在本地删了一节课，教务端未变。下一次刷新不应提示「教务新增课程」，也不能静默补回用户主动删除的课。

### 7.2 不完整响应不是减课

登录失效、请求失败、只返回部分分页、解析异常、课程大面积突降等情况不推进可信源基线、不生成普通减课通知。

沿用异常批次挂起与缺失观察规则。初次观察到单次缺失时先保留本地课，作为减少候选持续核验；默认沿用至少 3 次有效观察且跨越 48 小时才升级待确认，重复点击刷新不能按失败请求累积次数。

对比基线推进与缺失候选必须独立持久化：即使下一次可信源快照已记下，未解决的缺失候选仍需保存原课次并继续观察，否则“第一次少了，之后不再出现 diff”会导致永远无法确认减少。

调课／增加有可信完整响应及可靠匹配证据时可以直接进入待采纳；不需要无差别等 48 小时。

### 7.3 通知保持一行摘要

```text
发现课表变更：调课 1 节 · 减少 1 节 · 增加 2 节
```

仅显示非零类别；点击后分三组列出具体课程与时间。未采纳前使用「发现变更／待确认」，不能提前写成「课表已更新」。采纳提交后才显示「课表已更新」。

首期“通知”指现有时间表内提示条和变更面板，沿用现有刷新触发时机；不额外增加后台轮询、系统推送或通知权限申请。若后续需要系统通知，再单独定义后台检测频率和提醒策略。

- 同一来源和变化指纹不反复提醒；保留“查看”与“处理”的区别。
- “查看过”不等于“已采纳”，待处理事项不因打开面板就消失。
- 忽略只记住该次变化指纹；教务之后又发生不同变化时应重新出现。
- 多个课表／学期分别计数，不能串到当前显示的课表。
- 用户可按条采纳或保留本地；调课是旧课次和新课次的一个原子操作，不允许只采纳其中一半。
- 减少候选待核验时可在详情写「源端暂未返回，已保留本地」，不把它当成已确认减少计入主摘要。

## 8. 数据与事务设计

建议新建统一版本仓储，而不是继续用删除历史回放拼接版本。

### 8.1 建议模型

`TimetableVersion`：

- `id`、`ownerKey`、`timetableId`、`termId`（本地课表可无教务学期标识）。
- 单调 `revision`、`parentVersionId`、`committedAtMillis`。
- `reason`、可选 `restoredFromVersionId`、规范化内容指纹。
- 有版本号的完整课程快照载荷，包含源身份、逻辑课次身份和隐藏状态。

另存当前版本指针及源比对状态。源比对状态至少区分可信已观察快照、最近已采纳基线、未处理差异和缺失候选；不占用五条版本配额。

裁剪后父版本可能已不在保留集中，按“浅历史”处理：完整快照独立可用，不通过父版本外键级联删除整个版本链。

### 8.2 建议存储与原子性

建议版本元数据、快照载荷及当前版本指针存 Room：课程写入、版本追加、当前指针更新和历史裁剪能在同一事务完成。正式实现预计需要 Room v19 → v20 显式迁移及导出 schema；最终表结构在实现前细化，不承诺零数据库迁移。

每次写操作必须在实际提交边界生成一个版本，而不是让 Activity 保存快照。接入范围包括统一写入口、教务采纳、跟读／培养方案采纳、ICS／口令导入、隐藏／恢复、开学日期和作息改动。

现有文件型教务变更状态在第一阶段继续通过 `TimetableChangeRecovery` 的 durable outbox 发布。新版本若已进入 Room，不再重复向旧快照文件写一份用户版本；需要同步发布的通知摘要保留可重放、幂等的 outbox 语义。

写入失败不能留下“有版本但没改课”或“改了课却没版本”的状态。文件发布失败不能把已提交的课程操作报成未成功，避免重复恢复或重复采纳。

### 8.3 容量约束

五条是每个课表的上限，不是任意大小快照的豁免。沿用或补齐课程数量、课次数量及序列化字节上限；不允许静默截断快照，也不能让过大版本造成主线程阻塞或游标载荷超限。具体数值应结合现有导入上限与最大 fixture 测量后确定，元数据列表查询不得带出全部快照大字段。

## 9. 旧数据过渡

1. 首次升级时，从数据库当前实际课程建立一条完整基线，不能根据零散删除记录补造过去版本。
2. 旧教务快照缺少完整本地课程和隐藏状态，不能直接标成可完整恢复的新版本。
3. 首期保留一个标注清楚的兼容入口「旧教务快照（仅教务课程）」；也可在明确预览边界后，将旧快照应用到当前课程副本，生成新的完整版本。不能默认补成“历史全课表”。

## 11. 必须覆盖的验证

### 纯逻辑

- 同名不同教学班不合并；随机 UUID 重建不产生全量新增／减少。
- 同一课次 A → B 显示一条调课；增加、减少计数不重复。
- 跨周、跨日、节数变化、作息变更、多次重复课次和有歧义的多对多变更。
- 没有配对补课的缺失、分两次响应才出现的补课，以及候选变更更新／撤回。
- 正反向 diff 与恢复影响统计正确；地点／教师变化不误计调课。

### 存储与迁移

- 一次批量改课只产生一版；无变化／取消／失败不产生版本。
- 连续修改超过五次后只保留五版；源基线与缺失候选不被裁剪。
- 删到空课表仍可回退；恢复旧版创建新提交，而不是覆盖旧历史。
- 注入课程、版本、指针和历史裁剪失败，确认事务整体回滚。
- 查看 diff 后并发修改，恢复必须拒绝旧预览并要求重新比较。
- 账号、校区、学期、不同课表与本地课表隔离；旧文件损坏不能导致新版本库丢失。

### 刷新与设备

- 教务三校区真实格式的脱敏 fixture；登录失效、部分分页和异常空响应不误删。
- 本地删课／恢复旧版后，源端未变时不反复通知新增或静默覆盖本地。
- 同一变化多次刷新只提示一次，查看面板不等于采纳，调课只能整条采纳。
- 真机检查顶栏入口、版本时间、diff 标记、恢复后的网格／时间线／小组件与提醒刷新。
- Debug 构建、适当范围 JVM 测试、数据库迁移与事务设备测试、仓库检查分别报告；构建不能代替真机行为证据。
